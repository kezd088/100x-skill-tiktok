## 2. workflow.md phases → Dify nodes

**Phase 1 (人物反推)** splits into a scan/extract pair run twice (identify, then iterate): `llm_identify_candidates` mirrors workflow.md's step "通读脚本标出候选说话人切换点" (outputs a JSON array of speaker hints, or `[]` on the documented "no first-person viewpoint" failure path); `code_parse_candidates` parses that array and gates on count via `if_has_candidates` — the false branch (`tpl_no_persona_signal` → `end_no_persona_signal`) reproduces workflow.md's exact Phase-1 failure copy instead of guessing. The true branch feeds `iteration_phase1_personas`, whose inner `llm_extract_persona` node does the real per-candidate work: scans Authority (module 2) and Pain (module 3) signals, demands verbatim quotes, infers `delivery_style`/`relationship_to_camera`, implements the weak-signal degrade path (strongest-tone sentence + a `degraded`/`degrade_reason` flag), and self-scans its own `authority_evidence_quote` against the closed hedge-marker list so it can proactively emit a `meta.warnings`-shaped disclosure (`hedge_self_flagged`/`hedge_note`) — `code_assemble_personas` turns the resulting array of per-persona JSON strings into the `personas` map with generated `PERSONA_N` keys and folds `degraded`/`hedge_self_flagged` into properly-formatted warning strings. **Phase 2 (场景建模+关联)** mirrors this exact same scan→gate→iterate→assemble shape for scenes (`llm_identify_scene_clusters` → `code_parse_scene_clusters` → `if_has_scenes`/failure branch → `iteration_phase2_scenes` → `llm_extract_scene`, explicitly instructed never to merge the same persona's two locations into one scene → `code_assemble_scenes`), followed by `llm_build_pairings` (binds `script_span_quote` + `persona_ref` + `scene_ref` + `rationale`, told to aim for zero-orphan coverage and to backfill `segment_ref` from the optional `segments_json` start variable only when non-empty — the class-C silent-skip contract) and `code_parse_pairings`. **Phase 3 (输出)** is `code_assemble_bundle` (assembles the `PersonaSceneBundle` shape + a debug `bundle_json`) → `code_validate_bundle` (the axiom gate, see below) → `if_bundle_valid`, whose true branch writes personas/scenes back to the KB (`iteration_kb_write_personas` → `iteration_kb_write_scenes`) before `end_success`, and whose false branch renders every specific failing check via `tpl_render_failure_report` before `end_validation_failed` — never a generic "please recheck".

## 3. What could not be faithfully ported (read this before trusting the output)

**(a) The structural/schema layer is a hand-written Python approximation, not a real JSON-Schema validator — this is the single biggest fidelity gap.** The source skill enforces its schema by compiling `schema.json` through `ajv`, a real draft-07 validator, precisely because an earlier hand-rolled checker silently failed to enforce `additionalProperties:false` and the `relationship_to_camera` enum. Dify's sandboxed `code` node cannot `import` ajv or `jsonschema` (relying on Python standard library only), so `code_validate_bundle` is *necessarily* a hand-rolled re-implementation of everything schema.json declares structurally: required fields, `additionalProperties:false` on the root/`persona_item`/`scene_item`/`pairing_item` (checked field-by-field — I confirmed `meta`'s `additionalProperties:true` from schema.json and deliberately did *not* add an extra-fields check there, unlike the other four objects), the `relationship_to_camera` enum, `minLength`/`minItems`, and the `PERSONA_`/`SCENE_` ID-format patterns. I ported every constraint I could find in schema.json as carefully as I could, but this code node carries exactly the same class of risk ajv was introduced to eliminate: it is scoped to this one schema by hand and has no structural guarantee against drifting from `schema.json` if either file is edited later without the other. Treat it as "best-effort schema-shape approximation," not as ajv-equivalent, and say so if anyone asks whether this DSL enforces schema.json with the same rigor the source repo does.

**(b) The hedge-detection gap is preserved exactly, not altered.** `code_validate_bundle`'s hedge-marker block is a line-for-line port of `scripts/validate.js`'s `checkAuthorityHedgeRisk`: the same 20-item closed list (11 English + 9 Chinese phrases), scoped only to `authority_evidence_quote` (not `audience_pain_quote`/`script_span_quote`, for the same reason the source gives — negation there is often legitimate content), requiring a `meta.warnings` entry containing both the persona id and one of `hedge|自我怀疑|信任反转|待核` (case-insensitive) or the bundle fails. **It inherits the identical, explicitly-documented blind spot**: reversal via refutation/sarcasm framing (axioms.md's own worked example — quoting "trust me, I am a doctor" out of a passage that is mocking that exact claim) or via translation is not detected, because detecting it requires understanding semantic direction, not matching a closed phrase list — a limitation of string matching itself, not of this port. I did not attempt to add any LLM-judged semantic-reversal check to close this gap, preserving the exact limitation rather than introducing unverified heuristics. One partial mitigation *is* new to this Dify port and goes beyond the source's mechanism: `llm_extract_persona` is prompted to self-scan its own candidate quote against the same closed list and proactively emit a disclosure (`hedge_self_flagged`/`hedge_note`), which `code_assemble_personas` turns into a properly-shaped `meta.warnings` entry — this gives the pipeline a chance to pass autonomously on a hedge-marker hit instead of always hard-stopping, but it is a best-effort LLM self-check, not a guarantee (a careless or adversarial generation could still skip it, in which case `code_validate_bundle` still independently re-scans and hard-fails exactly as the source script would).

**(c) No automatic retry loop.** workflow.md Phase 3's rework table describes targeted, human-triggered rework ("这个人设不太对" → redo only that persona; "整批重来" → redo everything). This DSL is a one-shot pipeline: on validation failure it terminates at `end_validation_failed` with every specific failing check listed, but it does not wrap Phase 1–3 in a Dify `loop` container that automatically feeds the error list back into the extraction LLMs and retries just the failing item. The design deliberately routes to an end node that surfaces specific failures; a production deployment might additionally want a bounded retry loop, which would add meaningful complexity (loop-scoped state for "which specific persona/scene needs redoing" is nontrivial to wire correctly).

**(d) Two closed lists are hardcoded with no shared source of truth.** The vague-word list (axiom 3) and the hedge-marker list (the authority hedge mitigation) are both copied as Python literals into `code_validate_bundle` (and restated in the two extraction LLMs' prompts as instructions). If `axioms.md`/`schema.json`/`scripts/validate.js` in the source repo ever change these lists, this Dify DSL will silently drift out of sync — there is no mechanism to import the source repo's lists at Dify runtime. This mirrors a caveat the source repo already documents for itself (both lists are "凭经验列出的...未经真实语料验证覆盖率"), so the underlying lists were never claimed to be complete — but the *duplication* risk is new to this port and worth flagging separately.

**(e) "Same persona in two locations must become two scene_items" is instruction-only, same as the source.** This rule is stated explicitly in `llm_identify_scene_clusters`'s system prompt, but nothing downstream can mechanically detect "the model illegitimately merged two real locations into one scene_item" — this matches the source skill exactly (`axioms.md` says outright that axiom 4 "挡不住这种滥造，只能挡'定义了不用'"), so this is not a new gap introduced by the port, just carried over unchanged.

**(f) Scale untested.** Same caveat `axioms.md`'s own TODO section records for the source skill: only 1–2 personas/1–2 scenes were exercised (via the three `evals/*.json` files I read for calibration). The iteration nodes and the aggregated failure-report template are written to be N-agnostic, but readability of `code_validate_bundle`'s error list at, say, 5+ personas/scenes was not tested here either.

## 4. Final validator output (verbatim)

```
$ python scripts/validate_dsl.py --strict --target-version 0.7.0 100x-persona.dify.yml
== ...\dify-apps\100x-persona.dify.yml
WARN [node.unknown-type] workflow.graph.nodes[30].data.type: Node type 'knowledge-index' is not covered by a strict schema; dynamic outputs will be accepted.
WARN [node.unknown-type] workflow.graph.nodes[34].data.type: Node type 'knowledge-index' is not covered by a strict schema; dynamic outputs will be accepted.
0 error(s), 2 warning(s)
```

Exit code is 1 only because `--strict` promotes warnings to failing status; there are **0 real errors**. Both warnings are the same message, one per `knowledge-index` node (`kb_index_persona`, `kb_index_scene`). This is a gap in this third-party local validator script, not in the DSL: `knowledge-index` is a real, documented Dify node type (listed in the "Official Node Type Set" in `references/dsl-structure.md` and given a full field schema in `references/node-schemas.md`), but `dify_dsl_validator/validator.py`'s `_validate_node` method's type-dispatch `elif` chain never added a case for it, so it falls through to the generic "unknown node type, outputs accepted dynamically" branch, which always warns. I did not modify the validator to silence this (out of scope, and not requested) — the two `knowledge-index` nodes implement the KB-write-back design, so the warning is accepted and documented here rather than avoided.
