# 100x-segment → Dify Workflow DSL — porting notes

Source skill: `skills/100x-segment/` (v1.0.0)
Output: `100x-segment.dify.yml` — `app.mode: workflow`, `version: "0.7.0"`, `kind: app`, 16 nodes / 16 edges.

## 1. What needs manual reconnection after import

- **Model selection (all 4 LLM nodes)**: `detect_language`, `segment_l1`, `predict_shots`, `annotate_breaths` all use the placeholder `model.provider: langgenius/openai/openai` / `model.name: gpt-4o-mini`. A matching `dependencies[0]` marketplace entry (`langgenius/openai:0.0.20@<placeholder hash>`) was added purely so the DSL's own internal provider/dependency consistency check is satisfied — the identifier and hash are not real. Reselect the actual model/provider available in the target workspace for all four nodes after import; nothing else in the graph depends on which specific model is chosen.
- **`source_text` start-variable `max_length: 8000`**: a reasonable guess for a TikTok/UGC voiceover script (typically well under 1–2k characters); raise it if longer scripts are expected.
- **Code-node output `type: boolean`** (`missing_input`, `language_ok`, `parse_l1_ok`, `is_valid`): the local structural validator does not check this sub-field at all for `code` nodes (confirmed by reading `dify_dsl_validator/validator.py`'s `code` branch — it only checks that `outputs` is a mapping and uses the keys), so this carries zero risk against the structural validator requirements. I'm reasonably confident current Dify (1.16.x line / DSL 0.7.0) supports `boolean` as a native code-node output type, but if the target workspace's UI doesn't offer that exact label, it's a one-field cosmetic fix (switch to `string` and compare `"true"`/`"false"`) — everything downstream (the `if-else` conditions) already compares against the string literal `"true"` with `varType: boolean`, which is unaffected either way.
- Nothing else needs rewiring — nodes, edges, `variables[].value_selector`, and `end` node `outputs[].value_selector` all reference real, declared upstream outputs (verified against the validator's own reference-resolution pass, see §4).

## 2. workflow.md phases → nodes

**Phase 1 (接收+校验)** maps to `start` (the single class-A field `source_text`, `required: true`) → `intake_check` (code node: trims/checks emptiness, holding the exact fixed rejection template `"100x-segment 需要一段口播脚本的纯文本。没有文本无法分段——请把脚本贴过来。"`) → `intake_gate` (if-else) → either `reject_class_a` (end) or onward to `detect_language` (llm) → `parse_language` (code node: normalizes the LLM's raw output to `en`/`es`/`other`, holding the exact fixed rejection template for out-of-scope language) → `language_gate` (if-else) → either `reject_language` (end) or onward into Phase 2. **Phase 2A/2B/2C** (three *independent, overlaid* cut layers, not a competing sequential pipeline, per the skill's own framing) map to three LLM nodes: `segment_l1` (module 10-enum + archetype format, prompted with the full workflow.md 2A signal table) → `parse_l1` (code node, JSON-parses 2A's output) fans out in parallel to `predict_shots` (2B, module→shot_purpose heuristic table) and `annotate_breaths` (2C, the full axioms.md 公理3 priority-rule table), both of which only depend on `parse_l1`, not on each other — mirroring "L1/L2/L3 are independently overlaid views" rather than a forced serial chain. **Phase 2D (自检+渲染，合并)** maps to one code node, `validate_bundle`, which re-assembles the final `SegmentBundle` from the three LLM outputs and re-implements, in plain Python (stdlib `json`/`re` only — no `jsonschema`), everything `schema.json`+ajv would enforce (required fields, `enum` membership, the `archetype` backreference pattern, `additionalProperties:false`, `minItems`/`uniqueItems`) *and* everything `scripts/validate.js`'s hand-written layer enforces (axiom 2 `checkIntegrity`, axiom 3 `checkBreathPlacement`'s full priority cascade + mandatory-presence + run-cap + two soft warnings, axiom 4 `checkSequentialIds` + `checkShotSegmentLinkage`) — followed by `validation_gate` (if-else) routing to `segment_success` (end: full bundle JSON + rendered Markdown table + warnings) or `segment_failure` (end: the specific list of failing checks, `error_report` as a human-readable joined string, plus the best-effort partial bundle for debugging). **Phase 3 (用户触发返工)** is inherently a multi-turn conversational loop keyed to natural-language trigger phrases ("这段模块不对" / "这个镜头不对" / "这里气口不对") — that does not map onto a one-shot `workflow`-mode graph at all (this app has no chat turn structure to catch a follow-up correction against), so it is intentionally **not** represented as graph nodes; re-running the workflow with edited `source_text` is the closest workflow-mode equivalent, and this is disclosed here rather than silently dropped.

## 3. What could not be faithfully ported, and why

**(a) Archetype semantic grounding for letters A/B/C/D/F — a source-material gap, not a shortcut taken here.** `schema.json`/`axioms.md` only give the *machine-checkable format* for `archetype` (single letter A–G, or two *different* letters as `PRIMARY+SECONDARY`) — that regex (`^([A-G])(\+(?!\1)[A-G])?$`, backreference-excluding `"X+X"`) **is ported with full fidelity** in `validate_bundle` and independently verified (see §4). But the *narrative meaning* of each letter lives in a private taxonomy file (`口播文案蓝图·11模块7原型.md` §3) that this public skill deliberately never quotes verbatim (per this repo's own confidentiality rule against reproducing private-repo file content) — `axioms.md` only discloses two of the seven letters informally (E = reversal/reverse-psychology technique, G = suspense/secret-experiment-reveal skeleton) while explaining *why* module 11 is excluded and how mixed archetypes are written. The original skill's own operator (an agent with local filesystem access to that private path) could open that file to ground the other five letters; a portable Dify Cloud workflow structurally cannot reach that path, and reproducing its contents here would itself violate this repo's own open-source hygiene rule. `segment_l1`'s prompt is honest about this: it gives the two known definitions, states plainly that A/B/C/D/F's definitions are unavailable, and asks for an internally-consistent best-effort guess flagged as low-confidence rather than a fabricated definition. **This is a fidelity gap in what any public port of this skill can achieve, not something weakened in this port specifically** — and it only affects the *generative* quality of one field, never the machine-verifiable format check.

**(b) No auto-retry loop on validation failure — a deliberate single-pass design choice, flagged here for transparency.** The graph uses single-shot generate → validate → branch with if-else to route on pass/fail to an end that surfaces specific failing checks, rather than a `loop` node that re-invokes the LLM nodes on failure. This matters in practice for axiom 3's run-length cap: a *first-pass* breath-mark attempt can exceed the syllable cap on long or run-on scripts, which validate.js will reject. The same is structurally possible here — `annotate_breaths`'s first LLM attempt on a long or run-on Spanish script can land in `segment_failure` rather than passing on the first try, mirroring the underlying prompt-calibration dynamic rather than a defect introduced by this port. A user who wants auto-retry would need to add a `loop` node wrapping Phase 2, which was intentionally not built since it would add real complexity (loop variables, break conditions, nested container edges).

**(c) Three new `[pipeline]`-tagged glue checks, clearly distinguished from the four ported axioms.** Splitting one coherent generative phase (in the original skill, a single agent turn producing one JSON object) across three separate Dify LLM node calls (2A/2B/2C) introduces failure modes the original never had to handle: malformed/non-JSON LLM output from any of the three calls, and a `segment_id` produced by 2A having no matching entry from 2C's independent breath-annotation pass. `validate_bundle` catches all three and reports them with an explicit `[pipeline]` prefix — deliberately *not* `[axiom2]`/`[axiom3]`/`[axiom4]`/`[schema]` — so a failure report never misattributes a Dify-architecture-specific plumbing issue to one of the skill's own axioms. This is additive glue code required by the port, not a new axiom invented on top of the source material.

**(d) Knowledge Base wiring was skipped by design.** This skill's output is a segmentation of the *one script it was just given* — not a reusable named-entity/persona library the way a persona or scene-library skill's output would be — so no `knowledge-retrieval`/`knowledge-index` nodes were added.

**Everything else is a faithful, same-strictness, tested port**: axiom 1 (module 10-enum + archetype pattern), axiom 2 (`text_annotated`/`raw_text` cross-field integrity), axiom 3 (all 5 priority rules in the documented order — contrastive-conjunction > sentence-end/em-dash > comma/semicolon > forced run-cap break > soft filler-word suggestion — plus the mandatory sentence-end/em-dash presence check, the finite/non-exhaustive `ABBREVIATIONS` dictionary, the `!`/`?` zero-space-glue fix that deliberately does **not** extend to `.` [preserved exactly as the documented, deliberate asymmetry — not "fixed"], the naive vowel-group ES syllable estimator [preserved as-is, not replaced with a real syllabifier], and both soft non-blocking warnings [filler-word follow-up, price/number pre-mark]), and axiom 4 (sequential 1-based ids, referential integrity, zero-orphan coverage). None of these were strengthened, loosened, or "fixed" beyond what `scripts/validate.js` itself already does — including the `"so much"`/`"so many"` partial (not complete) mitigation for the `so`-as-intensifier ambiguity, which is reproduced exactly (both in the ported code's `SO_INTENSIFIER_RE` and in the `annotate_breaths` prompt's own explanation of the same partial mitigation) rather than "improved" past what the source skill's own TODOs say is still unsolved.
