# 100x-exaggerate · 核心约束（公理）

> 本 skill 建立了夸张轴与反差轴的枚举闭集。以下 4 条公理的枚举值（5 个夸张
> 技法 + 4 个反差类型）不是拍脑袋定的，逐条标出取自创意桥段词典哪个 L1 桥段/画面类型、
> 脚本结构公式库哪个结构型、或参考语料哪个 `matched_scenes` 信号的具体出现频次——
> 这是本 skill 遵守的判据设计原则（"有真实反例支撑再定判据，不要
> 拍脑袋编"），完整推导过程见 `sources.md`。

## 公理 1：夸张/反差手法须选自闭集枚举，不许自造

**一句话（21 字）**：夸张反差手法须选自闭集枚举，不许自创新词。

**可验证**：
- `exaggeration_beats[].technique` 落在 5 值闭集枚举内——`schema.json`
  `#/definitions/exaggeration_beat_item/properties/technique` 用 `enum` 硬锁
- `contrast_beats[].contrast_type` 落在 4 值闭集枚举内——`schema.json`
  `#/definitions/contrast_beat_item/properties/contrast_type` 用 `enum` 硬锁
- 以上两条 `schema.json`（经 ajv 编译）本身就能拦住，不需要 `scripts/validate.js`
  额外做聚合判断——闭集成员资格是纯粹的单条目校验，不是跨条目聚合，这条和
  `100x-search-query` 公理 3 的 `stage` 枚举、`100x-persona` 公理 1 的 ID 格式校验
  是同一类"schema 直接能管"的判据

## 公理 2：每条锚点须是脚本逐字子串，不许编造

**一句话（18 字）**：每条锚点须是脚本逐字子串，不许编造。

**可验证**：
- `exaggeration_beats[].script_span_quote` 非空——`schema.json` `minLength:1` 能管
- `contrast_beats[].anchor_quote_a` / `anchor_quote_b` 非空——同上
- **但"这段引文是否真的一字不差出现在 `source_script` 里，还是被改写/概括/翻译过"——
  这是跨字段比对（拿一个字符串字段去匹配文档里另一个字段的内容），`schema.json`
  完全没有这种能力**（JSON Schema draft-07 无法让一个属性的取值依赖另一个属性的内容）。
  这条由 `scripts/validate.js` 的 `checkQuoteSubstrings` 用 `source_script.includes(quote)`
  实际执行（大小写敏感、逐字符匹配，不做同义改写容忍）

**出处**：
- 判据设计直接沿用 `100x-persona/axioms.md` 公理 2（"人物的权威/受众依据必须是原文逐字
  子串，不许臆造"）的同一机制——两个 skill 都是"从脚本反推/设计标注，标注必须能倒查回
  原文"这一类生成型任务，`100x-persona` 已经证明这条判据机器可验证且能抓到真实退化案例
  （见该 skill `sources.md` 反例记录），本 skill 直接复用同一实现方式，不是重新发明
- 词典-06 本身对"桥段标注"的要求也隐含"标注要对应脚本里真实存在的内容"这个精神
  （Part 6 防滥用规则第 3 条讲的是"未能归类的内容不应阻断整体生成流程"这层意思，
  具体措辞不逐字引用——隐含的前提是标注要基于脚本本身能判断的内容，而不是脱离脚本
  编造）——但词典-06 面对的是"识别已有视频"的分析场景，
  本 skill 面对的是"从文本脚本设计新标注"的生成场景，具体的"逐字子串"判据是本次转译，
  不是词典-06 原文就有的机器判据

**反例（作废，对应 `--selftest` 第 4 项）**：
- `script_span_quote: "Doctors unanimously agree this is a miracle"`，但 `source_script`
  里从未出现这句话（是编出来的概括/复述，不是原文子串）→ `scripts/validate.js` 判 FAIL
- `anchor_quote_a` 写成对原文某段的中文翻译或意译，而不是原文语言的逐字摘录 → 同样
  不是字面子串，同一检查判 FAIL

## 公理 3：强度受市场帽度天花板校准，并非越夸张越好

**一句话（21 字）**：强度受市场帽度天花板校准，并非越夸张越好。

**这条公理直接回应词典-06 自带的校准注记**——第 216 行给出一条定性提醒：美区市场对
情绪化夸张的容忍度相对更低，渲染过度容易显得不真实，画面类型 H2 子类（第 726 行）表达
的是同一层意思（具体措辞均不逐字引用）——**这两处提醒都只针对"情绪反应"这一个维度，
不是笼统地说"所有夸张都要收着写"**。词典-06"帽度倾向"一节（第 903-915 行）另外按
黑帽/灰帽/白帽三档分别给出了不依赖具体维度的定性强度倾向描述（907-914 行：黑帽方向
允许的强度更高、可按品类和受众调整；灰帽方向整体偏低强度或中性；白帽方向整体保持中性，
具体措辞不逐字引用）。本公理把这两处**定性描述**转译成一张**机器可执行的天花板表**
（这是本次原创的具体数值化判断，词典-06 本身没有给出数字化的强度上限表，见下方
"原创判断披露"）。

**可验证**：
- `exaggeration_beats[].intensity` 落在 `mild/moderate/aggressive` 三值闭集
  ——这一层 `schema.json` `enum` 能管
- **但"这个 `intensity` 值是否超过了 `meta.hat_level` + `meta.market` 两个字段共同
  决定的天花板"——这是一个由两个兄弟字段共同决定的查表函数，`schema.json` 没有任何
  关键字能表达"根据字段 A 和字段 B 的字符串值查表得到字段 C 的合法上界"这种逻辑**
  （即使 JSON Schema draft-07 的 `if/then` 能处理"整份文档满足条件 X 则整份文档必须
  满足 Y"这种单一条件分支，这里的天花板是"技法 × 帽度 × 市场"三个维度的组合查表，
  用 `if/then` 硬编码会退化成大量重复分支，本质上仍是在 schema 里重新实现一个函数，
  违背了"schema 表达不了的才手写"的分工原则）。这条由 `scripts/validate.js` 的
  `calibrationCheck` 函数实际执行（内含 `BASE_CEILING_BY_HAT_LEVEL` 查表 +
  `emotionCeilingForMarket` 查表两级）

**天花板表（`scripts/validate.js` 与本节必须逐字同步，改一处必须同步改另一处）**：

| hat_level | 基线天花板 | 说明 |
|---|---|---|
| `whitehat` | `mild` | 词典-06"帽度倾向"一节对白帽方向的定性描述是全程保持中性呈现（913-914 行，具体措辞不逐字引用）——中性呈现本身不承载黑帽强度的夸张手法，本 skill 把这条定性判断落地为"任何技法都不超过 mild" |
| `grayhat` | `moderate` | 词典-06"帽度倾向"一节对灰帽方向的定性描述是以低强度黑帽或中性呈现为主（910-911 行，具体措辞不逐字引用）——"低强度"直接对应 `moderate` 档 |
| `blackhat` | `aggressive` | 词典-06"帽度倾向"一节对黑帽方向的定性描述是强度可按品类和受众调整、允许更高（907-908 行，具体措辞不逐字引用）——blackhat 允许拉满到 `aggressive`，但下面这条针对 `emotion_reaction_hyperbole` 的市场特例仍然生效，不因为 hat_level 是 blackhat 就豁免 |

**`emotion_reaction_hyperbole` 技法专属的市场特例（唯一一个不只看 hat_level 的例外）**：
如果 `meta.market` 命中美区别名（`美区`/`美国`/`us`/`usa`/`united states`/`america`），
`emotion_reaction_hyperbole` 这一个技法的天花板额外收紧到 `moderate`，**即使
`hat_level` 是 `blackhat`（基线允许 `aggressive`）也不例外**——这是词典-06 校准注记
明确点名"美区"+"情绪"两个维度的直接落地，不对其余 4 个技法生效（词典-06 没有证据表明
数字/时间/类比/权威这四类夸张在美区同样需要收紧，本 skill 不替词典-06 无中生有地扩大
这条限制的适用范围）。

**"命中美区别名"的匹配方式**：`meta.market`
先按常见分隔符（逗号/顿号/分号/竖线/括号/连字符`-`/`&`，中英文标点都算，**不含空格**
——因为别名 `united states` 本身含空格，按空格拆会把它拆散成两段）切成若干段，再对
每一段做整体 trim + 大小写不敏感的**精确匹配**（不是子串匹配），命中任一整段即视为
美区。

**已知局限（如实披露，不是自我表扬）**：仍无法识别别名嵌在更长的中文复合词中间且
前后**没有任何分隔符**的写法（例如"美国市场"整体作为一段时不等于"美国"，不会被
判定命中美区，因为中文没有空格可用、本脚本也不做真正的分词/断词）。`schema.json`
对 `meta.market` 给出的示例本身就是"美区"/"US"/"西语区"/"通用"这类独立短描述，
本次判断这个更窄的匹配范围是可接受的权衡，但如实记录这仍是一个未解决的边界（见
文末 TODO）。

**`meta.market` 缺失时的默认值（原创判断，工程说明）**：`meta.market` 未提供时，
`emotionCeilingForMarket` 按**保守分支**处理（等同于命中美区别名，天花板收紧到
`moderate`），而不是按"没写就当作可以放开"处理。理由：不知道目标市场时，"误伤"（把
一条其实可以 aggressive 的情绪夸张收紧成 moderate）的下游代价，明显小于"误放"（一条
本该收紧的情绪夸张因为用户忘记填market字段而被放到aggressive，结果在真实美区投放时
显得失真）的下游代价，两者不对称，选保守分支。这与 `100x-search-query` 敏感品类检测
"宁可多提示不可漏提示"的保守化取向是同一种工程直觉，但本条判据本身是本次原创，
不是照搬 search-query 的具体规则。

**出处**：
- 词典-06 第 216 行、第 726 行（情绪维度的美区校准注记）
- 词典-06 第 903-915 行"帽度倾向"（三档定性描述）
- 天花板的具体数值化（`mild=1/moderate=2/aggressive=3` 三档 + 上表映射关系）**是本次
  原创判断，不是照搬某份文档的现成规则**（如实披露，见 `sources.md` "原创判断披露"）；
  `intensity` 三档命名本身直接借用参考语料 `blackhat_intensity` 字段的既有取值
  （该字段真实值为 `aggressive`/`moderate`/空白三档，`mild` 是本次为空白档补的命名，
  不是凭空发明第四档）

**反例（作废，对应 `--selftest` 第 6/7/8 项）**：
- `hat_level: "blackhat"` + `market: "美区"` + 一条 `technique: "emotion_reaction_hyperbole"`
  的 beat 标 `intensity: "aggressive"` → 超过市场特例天花板 `moderate`，
  `scripts/validate.js` 判 FAIL（`--selftest` 第 6 项）
- 同一条 beat，分别把 `market` 换成 `"西语区"`/`"Russia"`/`"Australia"`/`"Belarus"`/
  `"南美国家"` 这五个真实不命中美区别名的市场字符串（这些是回归用例——用于验证精确匹配
  不会把包含别名子串的市场误判成美区，见公理 3"命中美区别名的匹配方式"段）→ 天花板均恢复为
  blackhat 基线 `aggressive`，同一个 `intensity: "aggressive"` 这次全部判 PASS（`--selftest`
  第 7 项，证明这是真的按市场计算的天花板，不是"这个技法一律判不过"，也不是"字符串里看起来像
  美区就按美区处理"）
- 同一条 beat，分别把 `market` 换成 `"美区-通用"`/`"US & Canada"` 这两个用连字符/`&`
  组合了美区别名和其他值的市场字符串（这些是回归用例——用于验证分段符号列表包含 `-` 与 `&`，
  使组合多值写法里的美区别名仍能被正确识别，见公理 3"命中美区别名的匹配方式"段）→ 天花板
  均应收紧到市场特例上限 `moderate`，同一个 `intensity: "aggressive"` 这次全部判 FAIL
  （`--selftest` 第 8 项，证明组合多值写法里的美区别名仍能被正确识别）
- `hat_level: "whitehat"` + 任意技法标 `intensity: "aggressive"` → 超过白帽基线天花板
  `mild`，判 FAIL（本文件未单独列为 `--selftest` 编号，但 `calibrationCheck` 对
  whitehat/grayhat 走同一段代码路径，逻辑上与第 6 项同源）

## 公理 4：反差两端须有真实落差，不许同句充当两端

**一句话（20 字）**：反差两端须有真实落差，不许同句充当两端。

**可验证**：
- `contrast_beats[].anchor_quote_a` 与 `anchor_quote_b` 各自非空——`schema.json`
  `minLength:1` 能管
- **但"这两个字段的内容是否互相不同"——JSON Schema draft-07 没有任何关键字能表达
  "同一对象的两个兄弟字符串属性必须互不相等"，这是纯粹的跨字段比较，schema.json
  结构上表达不出来**。这条由 `scripts/validate.js` 的 `checkContrastNonDegenerate`
  函数实际执行：把两个字段各自 trim + 转小写 + 空白归一化后比较是否相等

**出处**：
- 词典-06 画面类型 D（对比冲击类画面，第 565-598 行）核心要素第 582 行明确要求：
  反差的两端要让观众感知到真实的视觉落差（具体措辞不逐字引用）——这是词典-06 里唯一
  一处**明确要求"反差的两端必须有真实落差"**的具体判据，本公理是这个要求的直接机器化：
  把"明显视觉落差"这个人工判断收紧成一个可以完全自动执行的最低门槛——"两端不能是
  同一句话"（连"落差"这个更高要求都够不到的最基本情况）

**已知局限（如实说明，不是自我表扬）**：这条检查只能拦住**完全相同**（大小写/空白
归一化后相等）的退化情况，拦不住"两端字面不同但语义上仍是同一件事换个说法"的更隐蔽
退化（例如 `anchor_quote_a: "her skin looked dull"` 配 `anchor_quote_b: "her skin
appeared dull"` ——字面不同，但语义零落差）。这与姊妹 skill `100x-persona` 自己
`axioms.md` 公理 3 TODO 里记录的"`micro_coordinate` 与 `location` 同义重复退化，
目前无法用正则拦截"是同一类天花板：**两个 skill 都只能拦"字面完全相同"，拦不住
"语义重复但字面不同"**，要堵住这个更深的漏洞需要相似度/编辑距离判据，本 skill 同样
判断"目前没有已验证的相似度阈值可用"，与 `100x-persona` 一样先不做，留 TODO（见文末）。
这里主动记录这个和 persona 同源的已知天花板，而不是假装本 skill 解决了 persona 没解决
的问题。

**反例（作废，对应 `--selftest` 第 5 项）**：
- `anchor_quote_a: "my under-eye skin looked so tired and crepey"`，
  `anchor_quote_b` 也写成完全相同的字符串（复制粘贴前者）→ 归一化后相等，
  `scripts/validate.js` 判 FAIL

## 为什么是这 4 条，不多不少

- 公理 1 是**结构基础**：夸张轴与反差轴需要建立明确的闭集枚举，没有这条闭集
  约束，整个 skill 的核心产出（技法+反差类型标注）就退化成"随口起名字"，
  跨脚本/跨批次不可聚合统计，和创意桥段词典要求桥段标注必须从固定大类集合中选择、不允许
  自创（第 80-81 行，具体措辞不逐字引用）的设计精神直接对应
- 公理 2 是**防臆造**：和 `100x-persona` 公理 2 同一防线——生成型 skill 最容易退化成
  "凭感觉编一句听起来对的引文"，逼着每条标注都能倒查回脚本原文
- 公理 3 是**本 skill 独有的边界公理**：创意桥段词典明确写了美区市场夸张强度需要收敛的校准注记（具体措辞不逐字引用，见公理 3），
  如果本 skill 只讲"技法怎么选、怎么标注"而不讲"强度有没有上限"，就是选择性无视素材里
  明摆着的边界条件。公理设计必须吸收这条边界，不能只讲"越夸张越好"
- 公理 4 是**防退化**：直接对应词典-06 Type D 自己写的"两端要有可感知落差"这一核心
  要求（具体措辞不逐字引用），防止"反差"这个概念被写成两句意思相同的话凑数

不采用"夸张点必须搭配至少一个反差点，两者必须成对出现"作为第 5 条公理——虽然
`exaggeration_beats`/`contrast_beats` 都要求 `minItems:1`，但没有找到素材依据支持
"每个夸张点必须有对应的反差点"这种一一绑定关系（词典-06 的 15 个 L1 桥段里，
`extreme_emotion_reaction` 和 `before_after_comparison` 是两个独立桥段，一条脚本
可以只用其中一类而不必然搭配另一类），勉强凑一条"绑定"公理会变成没有证据支撑的
拍脑袋规则，故不采用。
